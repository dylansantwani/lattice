## Slice 4 — context & cache engine (partial)

- [x] Manual compaction (`/compact` → `compactThread`): summarizes live history into one persisted summary message, marks folded messages `compacted` (kept for the reader, dropped from the wire), emits a `compaction` event. Occupancy is computed per model and drives the Context ring.
- [x] **Automatic threshold-triggered compaction + block enforcement.** The `compactionThreshold`/`blockThreshold` settings, previously inert, now drive real behavior. On send, once a thread's context (with the new message counted) crosses `compactionThreshold`, `maybeAutoCompact` folds the history behind the current turn into a summary automatically — the just-sent message is persisted first (instant feedback) and preserved live via `compactThread`'s new `preserveMessageId`, and the thread stays in its working state across the compaction (`keepRunning`) so there's no spinner flicker. Gated by a new `autoCompact` setting (on by default; Settings → Conversation). At `blockThreshold` the composer hard-stops a fresh turn — a red banner + disabled Execute + a warn flash tell the user to `/compact` or switch to a larger-context model, and the draft is kept (never sent, never lost); steering an in-flight run and slash commands route around the block. The Context Orbit's warm/hot ring now tracks the real thresholds instead of hardcoded 0.8/0.92. Covered by `autoCompact.test.ts`. Still open here: checkpoint/rollback of a compaction and locked turns.
- [x] **Real tokenizer-based token counting + stale tool-result pruning.** The chars/4 heuristic is gone — a real BPE encoder (`src/main/runtime/tokenizer.ts`, `gpt-tokenizer`, pure-JS/no-native) now backs `estTokens`/`countTokens`, choosing o200k_base (the modern frontier-model proxy) or cl100k_base (legacy GPT-4/3.5) by model family. Counting is content-memoized and hard-bounded — oversized strings and degenerate repeated-char runs (the encoder's quadratic worst case) divert to the ratio heuristic so a pasted mega-blob can never hang budgeting. `getContextBudget`, `wireMessageTokens`, tool-schema sizing, the `tokensOut` fallback, and compaction before/after all count for real now. **Stale pruning**: `buildWireMessages` replaces the result bodies of far-back tool turns (older than the most recent `TOOL_RESULT_KEEP_RECENT_TURNS`=6, and larger than `TOOL_RESULT_PRUNE_MIN_TOKENS`=512) — plus any tool-returned images — with a compact, *byte-stable* placeholder (`pruneStaleExchanges`), keeping the assistant↔tool pairing valid and the recent working set fully intact. The placeholder encodes only tool name + original size (never turn distance), so a result stays byte-identical once pruned and pruning costs the cache one write, not a per-turn churn. Gated by the `pruneToolResults` setting (on by default; Settings → Conversation), and the Context inspector reports the tokens reclaimed (`ContextBudget.prunedTokens`). Covered by `tokenizer.test.ts` + `toolPruning.test.ts` (24 tests); existing `contextBudget.test.ts`/`toolReplay.test.ts` still green.
- [x] Cache-metrics surfaces beyond the telemetry chip (2026-09-02): the Context inspector's **Prompt cache (last turn)** section shows tokens read from / written to cache and fresh, a verdict (hit / partial / cold / no activity / caching off), and the likely reasons for a miss — first turn, model changed, thinking effort changed (it is named in the system prompt), a compaction between the turns, more than five minutes since the previous turn, provider caching switched off, or a route that reports no cache activity (`cacheInsight.ts`, pure and unit-tested; `run.started` now records `promptCaching`, and `TurnUsage` keeps read/write apart).

## Slice 5 — orchestration (plan Phase 3, partial)

- [x] `run_agent` delegation: spawns an isolated subagent that shares the run's tool access, streams its own tagged events, and returns its final answer; accepts an optional per-call `tools` allowlist (validated against the real set before spawning) and cannot spawn further subagents.
- [x] **Background / async subagents**: `run_agent` gains `background: true` — it starts the subagent concurrently and returns a handle (`agentId` + `name`) immediately instead of blocking, so the main agent can keep working, or park on `ask_user` to hand control back to the person, while it runs. A new `agent_result` tool waits for (or, with `wait:false`, polls) the background agents and returns their results; spawn several to run independent work in parallel and collect them together. Each background agent is tracked on `ActiveRun.bgAgents` and awaited before the run finalizes, so none ever outlives its run; they share the parent abort, so cancel winds them down. `agent_result` mirrors `run_agent`'s policy profile (both withheld outside workspace/full), and both plus `set_thread_title` are stripped from subagents. Covered by `builtin.test.ts` + `toolDelivery.test.ts` (`builtin.ts`, `runManager.ts`, `tools/types.ts`).
- [x] **Peek at running subagents**: a new `peek_agents` tool lets the orchestrator check IN on its background subagents mid-flight — a live, read-only glance at what each is doing RIGHT NOW: current activity (`running <tool>` / `thinking` / `writing its response` / `finished`), the tool it is executing this instant, completed tool-call count, elapsed and idle time, and a tail of its latest output. Progress is folded from each subagent's own run events into an in-memory snapshot (`agentProgress.ts`, a pure reducer) kept on the thread-scoped `BgAgent`, so a peek needs neither a blocking wait nor an event-store read. Crucially it is purely observational: unlike `agent_result` with `wait:false` (which claims terminal agents so they aren't re-delivered), `peek_agents` never sets `delivered`, so a finished agent's result still arrives on its own as a `🤖` turn. Mirrors the `run_agent`/`agent_result` policy profile (network/execute/R0, withheld outside workspace/full) so the delegation trio is offered together; stripped from subagents and never delegatable. Covered by `agentProgress.test.ts` (reducer + activity phrasing), `builtin.test.ts` (tool wiring), and a `runManager.test.ts` end-to-end case that peeks at a still-running agent and proves the peek did not consume it (`builtin.ts`, `runManager.ts`, `agentProgress.ts`, `tools/types.ts`).
- [x] **Web search for agents**: `web_search` queries Bing's RSS endpoint and returns bounded, structured result titles/URLs/snippets/dates; `web_fetch` follows only public redirects and extracts bounded readable page text. Both are available to subagents through the normal inherited/explicit tool allowlist, warn that page content is untrusted, and use the existing network permission boundary with private-network/credential/scheme checks. Covered by `webTools.test.ts`, `toolDelivery.test.ts`, and `toolEffect.test.ts` (`webTools.ts`, `network.ts`, `builtin.ts`).
- [x] `/side` and `/btw` forks: `forkThread` seeds a child thread from the parent's history with `parentThreadId`/`parentEventId` recorded.
- [ ] Subagent templates; explicit parent-ceiling enforcement on delegated tool policy.
- [ ] Agents inspector tree; checkpoints/rewind (branch from event); promotion with provenance.

**Also landed (thread/run management, not previously tracked):** `/clear` (`clearThreadContent` + `cancelRunForThread`), and queue editing while a run is active — `dequeueMessage` / `editQueuedMessage`.

  - [x] **Background jobs — free the model from a long task (a download, a build, a big test run)** (`src/main/tools/bgJobs.ts`): `shell` gains `background: true`, which starts the command as its OWN detached child process (login `$SHELL -lc` for the real PATH — not the thread's serialized interactive PTY, not tied to the run's abort) and returns a `jobId` immediately instead of blocking. Fixes: (1) `shell(background:true)` now registers with the same notify-on-completion lane as an auto-promoted command, so a finished job is delivered as a `⏳` turn that wakes an idle thread (or is flushed when the busy run settles); `PendingShellJob.kind` keeps a deliberate job from pinning the thread's "running" flag (a background dev server must not spin it forever) while a timeout-promoted one still does. ## Known issues

- `externalizeDepsPlugin` does not externalize under pnpm 11 — explicit `NATIVE_EXTERNALS` list in `electron.vite.config.ts`; add new native/server deps there.
- Left rail occasionally starts collapsed on dev launch (state defaults to expanded; toggle is ⌘B) — root cause not yet found, low priority.
- Renderer settings modal edits only the first provider; multi-provider UI pending.
- Steering currently re-sends after stream completion (safe boundary = end of response); provider-level mid-stream injection not implemented.
- The approval flow is live (ApprovalBar sheet + `respondApproval`), but grants are only remembered in-memory per run/thread — there is no durable, cross-session saved-rule layer yet, and `profile` scope is treated as thread-wide.
- Real-provider tool-loop integration tests are still pending; the current UI smoke test uses a mocked bridge.
- Tool schemas are selected from the model registry's `capabilities.tools` flag; missing or incorrect provider metadata can prevent tool schemas from being sent.
- Filesystem reads/edits are bounded to 256 KB and use no-follow handles, but a fully atomic `openat`-style containment boundary is still a hardening task.
