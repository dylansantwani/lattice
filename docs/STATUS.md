# Lattice implementation status

**Snapshot:** 2026-08-31  
**Audience:** Dylan and future contributors working in this repository  
**Product shape:** macOS-first Electron desktop control room for model runs

This document is the implementation ledger. It describes what the current source tree does, what is only partially implemented, and what remains from the product plan. `docs/product-plan.md` remains the desired product direction; this file is the source of truth for the current working tree.

## Status vocabulary

- **Implemented:** present in the source tree and covered by the current typecheck/build path.
- **Partial:** a useful vertical slice exists, but an important production or UX piece is missing.
- **Planned:** represented in the product direction or data model but not implemented end-to-end.
- **Known issue:** implemented behavior has a documented limitation or needs follow-up hardening.

## What works today

### Desktop shell

Implemented in `src/main/index.ts` and `src/renderer/src/App.tsx`:

- Electron `BrowserWindow` with hidden inset title bar, traffic-light positioning, minimum window size, and macOS lifecycle handling.
- Renderer isolation: context isolation on, Node integration off, typed preload bridge, and a renderer content-security policy.
- External HTTP(S) links open through the host shell; navigation away from the app origin is blocked.
- Development builds expose Chromium remote debugging on port `9223` for UI inspection.
- Three-pane shell: thread sidebar, transcript/composer center, and inspector rail.

### Persistence and event model

Implemented in `src/main/store/db.ts` and `src/main/store/eventStore.ts`:

- SQLite database in the Electron user-data directory, using WAL mode and normal synchronous settings.
- Tables for workspaces, threads, messages, append-only run events, settings, todos, memory, permission-rule storage, MCP configurations, and model cache.
- Default workspace creation with the user's home directory as its initial approved root.
- Thread creation, listing, selection metadata, updates, archive/delete support, pin state, model, effort, mode, and permission preset.
- Messages persist role, text, attachments, model/effort, terminal status, and telemetry.
- Run events persist sequence numbers, timestamps, agent IDs, and typed event bodies.
- Memory and todo CRUD exists; model cache is keyed by provider and has a ten-minute freshness window with stale-cache fallback.
- **Hot-path performance:** SQL statements are compiled once and reused (`prep` in `db.ts`, ~18× per query vs. re-preparing), settings and the provider model listings are memoized in memory (all writes go through `setSettings`/`setCachedModels`, which keep the memos coherent; `resetStoreMemos` exists for raw-SQL test resets), and a `toolWireRevision` counter — bumped only when tool exchanges/compaction/deletion change what a wire would replay, never by streaming text flushes — lets wire-derived work (stale-pruning accounting) memoize across a whole streaming reply.

### Provider and model registry

Implemented in `src/main/providers/openaiCompat.ts`, `src/main/providers/registry.ts`, and `src/main/ipc.ts`:

- Multiple OpenAI-compatible providers are supported: Settings → Providers manages a list (add/edit/remove, per-provider enable and prompt-caching toggles). The model picker aggregates models from every enabled provider (`fetchAllModels`, first provider wins on a duplicate id) and each request resolves to the provider whose cached model listing serves the thread's model (`providerForModel`), falling back to the first enabled one.
- First launch seeds an OmniRoute provider at `http://localhost:20128` and discovers a key from `OMNI_KEY` or `~/.local/bin/omni-cc`.
- `/v1/models` responses are normalized into model ID, friendly name, route/provider, context length, max output, and capability flags.
- Capability normalization reads common provider metadata for tools, vision, reasoning, and effort tiers.
- Model requests use SSE streaming with defensive parsing for text, reasoning, tool-call deltas, usage, cache fields, reasoning tokens, cost, and finish reasons.
- Provider failures classify into auth, rate-limit, context, unavailable, and generic error categories.
- **Endpoint auto-retry** acts on that classification instead of just surfacing it: a round whose provider request fails *transiently* — 429, 408, any 5xx, or a network-level drop (ECONNRESET/refused/DNS/`terminated`), mid-stream included — is automatically redone rather than ending the turn. Policy lives in `src/main/runtime/endpointRetry.ts` (pure and unit-tested): `isRetryableEndpointError` gates on the transient set only (a 4xx that isn't 408/429 — bad auth, an over-long prompt, an unknown model — surfaces immediately, exactly as before), backoff is exponential with full jitter (500ms→20s ceiling) and obeys a `Retry-After` the endpoint sends (parsed from seconds *or* an HTTP date, capped at 60s; `ProviderHttpError` now carries the header), and `retryDelay` is a cancellable sleep so a user Stop rejects it and a steer wakes it early. Both the main turn loop and every subagent loop wrap the round's stream in the same bounded redo: before each attempt they snapshot the round's rollback point (`segmentText`/`text`/`reasoning`/`firstTokenAt`/`usage`) and reset the per-attempt buffers, so a **mid-stream** drop — bytes already streamed, then the socket died — restarts the round from clean state instead of stitching a broken half-reply onto the redo. The rollback is made visible by a `retry` event marked `rewound: true`: `buildTimeline` drops every reasoning/text/tool-draft delta the failed attempt streamed back to the last *committed* point (a completed tool lifecycle, a steer, a compaction, or a prior retry notice — never a bare draft), so the transcript shows only the successful reply plus a quiet inline "retrying (n/N)…" notice, live and after reload. Attempts are bounded by the `maxEndpointRetries` setting (default 4; 0 disables auto-retry entirely). Stall/length self-recoveries keep their partial output and omit `rewound`.
- Prompt caching (per-provider, on by default — `?? true` at the request sites, so configs saved before the toggle existed still cache) injects Anthropic-style `cache_control` breakpoints: one on the system block and up to two on the tail of the transcript — the last stampable message *whatever its role, tool results included* plus the one before it. Stamping the tail (rather than only the last user turn) is what keeps the hit rate high through agentic tool loops: each round's request caches the accumulated transcript so the next round reads it back instead of re-processing every tool result.
- **Byte-stable serialization** (the other half of the hit rate): when caching is on, EVERY message is normalized to parts form (`[{type:'text',text}]`), stamped or not. Without this, a message flaps between string and parts form as the moving tail markers pass over it, gateways hash the changed bytes, and the prefix match dies — measured live as 0% turn-over-turn on the Claude routes before the fix, 98–99% after. Verified against the real OmniRoute gateway by the opt-in live suite (`LATTICE_LIVE=1 npx vitest run src/main/providers/liveGateway.test.ts`): cc/claude-fable-5 hits 99% turn-over-turn and 85% on a tool-round tail; openrouter/meta/muse-spark-1.2-contributor reaches 96–97% once Meta's load-balanced replicas warm (per-turn variance there is upstream-side, not client-side). The same suite live-verifies on-demand memory recall (model calls `memory_search` for a memory-dependent question, skips it for arithmetic) and self-learning distillation (valid JSON learnings with sane types/scopes/confidence). Usage parsing (`mapUsage`) reconciles the two backend conventions — Anthropic reports `prompt_tokens` excluding freshly-written cache tokens, OpenAI-style folds cache reads into `prompt_tokens` and reports no write count — by adding the write count back so `tokensIn` is the true total input on every turn. The telemetry chip shows a real hit rate only when there are cache reads, a brass "primed" indicator on a cold cache-write turn, and nothing when the backend reports no cache activity (never a misleading constant "0% cached"). Caching only engages once the stable prefix crosses the model's minimum cacheable size (~1024 tokens), so short early turns legitimately show no cache chip.

### Run lifecycle

Implemented in `src/main/runtime/runManager.ts`:

- A thread has at most one active run in memory.
- User messages can start a run, steer at the next safe boundary, or queue a subsequent turn.
- Runs emit `run.started`, text/reasoning deltas, usage, errors, and `run.completed` events.
- Assistant text is flushed to the database in short batches while streaming.
- Runs support cancellation through `AbortController` and preserve interrupted output.
- Threads are auto-titled from a model-written summary and **kept fresh as the conversation evolves**, governed by title provenance (`ThreadMeta.titleSource`, persisted as `threads.title_source`): `auto` titles refresh on a geometric cadence — whenever the human-message count has at least tripled since the last titling (`shouldAutoTitle`) — so a chat named from "hi, quick question" is renamed once it becomes a three-hour refactor, while stable conversations never flap. A rename from the UI flips provenance to `user` and a model rename via `set_thread_title` to `agent`; both permanently stop auto-titling, re-verified at write time so a rename landing mid-summary is never clobbered. The summary call reads a bounded digest of the whole conversation (opening message + recent user turns + latest reply, `titleDigest`), and `cleanTitle` now also survives chatty models (preamble lines like "Sure! Here's a title:" are skipped) and reasoning leakage (`<think>` blocks stripped; an unterminated block yields no title rather than naming the chat with reasoning). The failure fallback trims the first user message at a word boundary and stays `auto`, so a weak fallback name self-heals at the next refresh threshold.
- Telemetry includes TTFT, wall time, model time approximation, tool time, output/input counts, reasoning/cache counts, cost, TPS, and an estimated flag when the provider lacks authoritative values.
- The base and subagent system prompts include an explicit execution contract: define outcomes and acceptance checks, inspect/discover capabilities, recover from failed or incomplete tool results with a changed strategy, independently verify deliverables, and audit every outcome before claiming completion. This improves model discipline; a normal text response is still terminal at the runtime layer, so automatic completion judging/retry remains a future controller feature.

### Tool runtime

The first execution slice and the interactive approval broker are now implemented.

Implemented in `src/main/tools/types.ts`, `src/main/tools/builtin.ts`, and `runManager.ts`:

- Typed tool definitions include JSON schema, resource, action, risk tier, plan-mode allowance, summaries, and an async runner.
- Built-ins: `fs_read`, `fs_write`, `fs_edit`, `fs_list`, `fs_mkdir`, `fs_move`, `fs_delete`, `shell`, `start_job`, `job_status`, `stop_job`, `grep_search`, `web_search`, `web_fetch`, `todo_write`, `memory_save`, `memory_search`, `show_image`, `show_image_data`, and `fetch_image`.
- **Deferred tool discovery** (`src/main/runtime/toolCatalog.ts`). Only the builtin core (~2.5k tokens of schema) is always sent. MCP tools are deferred: their schemas do NOT ride in every request — with a few servers connected they otherwise add tens of thousands of tokens of standing context. Instead the model gets one `find_tools` tool (offered only when the mode/preset would let some deferred tool run) and discovers capabilities by keyword; matches are loaded per-thread, append-only, and join the tool array from the next round of the same run (the loop recomputes its tool list each round). The system-prompt inventory lists only the stable core plus a static "more tools are discoverable" note, so loading a tool costs one cache write in the tools section instead of invalidating the prompt every turn after. The loaded set is persisted per thread (`thread_tools` table, write-through cached) so a relaunch does not forget it — the transcript keeps referencing loaded tools by name and the model re-calls them. A call to a connected deferred tool that is not loaded yet **loads it on first use** (`resolveToolCall` in runManager → `resolveDeferred`): Claude models know the `mcp__server__tool` names from Claude Code and skip `find_tools`, which used to bounce every such call with a bogus "unavailable under the current mode" denial (six in a row in one recorded run). Denials now say exactly why — withheld by plan/review mode or the permission preset, the per-thread cap, integration disabled/disconnected (with its connect error), or a genuinely unknown name — so the model corrects instead of retrying. A parent naming deferred tools in `run_agent`'s `tools` list pre-loads them for the subagent. Live-verified: asked for a browser screenshot with only the core exposed, the model calls `find_tools("browser screenshot page")`.
- Tool-capable models receive the active tool schemas on each provider request.
- Streamed tool-call deltas are assembled by call index, parsed, emitted as typed events, executed, returned as `tool` messages, and followed by another model request. As soon as a call's name streams in, a `tool.drafting` event surfaces it live (a "preparing" row) under the id the executed call will reuse, so the drafted and executed rows are one.
- The loop has a twelve-round guard and supports multiple calls in a single response.
- Tool events include approval-shaped proposed/approved, started, denied, and result states and are visible in the run inspector and transcript activity rows. Interactive approval is implemented (see the approval broker below).
- Tool schema tokens are included in context-budget accounting.
- Per-tool policy is decided by `toolEffect(tool, meta)` → `allow` | `ask` | `deny` (`src/main/runtime/runManager.ts`). Review and Manual expose only read-only R0 tools (`allow`), everything else `deny`. **Auto (workspace)** allows R0 reads/searches and approved-root R1 filesystem writes (`fs_write`, `fs_edit`, `fs_mkdir`, `fs_move`), and **`ask`s** for the shell and destructive file ops (R2 — `shell`, `fs_delete`), external network reads (`web_search`, `web_fetch`, `fetch_image`), and every MCP tool: they are offered to the model but each call is gated behind a user approval prompt. **Full** `allow`s the complete built-in set with no prompt.
- Filesystem paths are validated as strings, canonicalized through existing parents, checked against approved roots, and opened with no-follow flags where file handles are used. The path arguments to containment-check are resolved by `pathArgsFor`: an explicit `pathArgs` wins (multi-path tools such as `fs_move` declare `['from','to']` so each endpoint is checked), otherwise a filesystem tool is checked on `path` only when it actually declares a `path` parameter. This means store-backed tools that are tagged `filesystem` but take no path (`memory_save`, `memory_search`, `todo_write`) are no longer falsely rejected with "Invalid path … expected a string" (a bug that had blocked every memory/todo call). `fs_move`/`fs_delete` refuse to act on a workspace root itself, and `fs_delete` removes symlinks without following them. Reads and edits are bounded to 256 KB.
- `grep_search` uses shell-free `execFile` arguments, avoiding interpolation of model-controlled patterns and paths into a shell command.
- `web_search` queries Bing's RSS endpoint and returns bounded structured results; `web_fetch` follows only public HTTP(S) redirects and extracts bounded readable HTML/text/JSON. Both are available to subagents through the same inherited or explicit tool allowlist and mark returned web content as untrusted source material. Network tools use a shared public-host guard that rejects localhost, private/link-local/metadata addresses, embedded URL credentials, non-HTTP(S) schemes, and oversized bodies.
- **Where a turn's time goes — measured** (2026-09-02, six hours of live sessions + a raw-gateway probe; scripts in the session scratchpad). Per main-run round: Lattice's own overhead outside the HTTP call (wire prep, event writes, stream parsing) is **0.1–0.2 s at the median** (round wall minus the gateway's logged duration, matched per call). The wait for the model's first token after a tool result is **5.3 s p50 / 13.9 s p90 on `openrouter/z-ai/glm-5.3-flash`** and **3.2 s / 5.4 s on `cx/gpt-5.6-luna`**; tool execution is 0 s at the median. A bare streaming request to the same gateway shows the floor is the provider, not the harness: GLM's first token takes 3–7 s even for a 19-token prompt and 2.2–3.0 s for a replayed 21k-token Lattice payload (then 10–15 s of reasoning for 24 output tokens); Luna 1.8–4.2 s. The multiplier is **rounds**: GLM averages 7.8 rounds per turn, Luna 4.9, and 91–96 % of rounds carry a single tool call (`shell` alone is 393 of ~700 calls) — so a turn spends ~8 × 5 s just waiting for first tokens. Levers that keep quality: (1) **fewer rounds** — the execution contract now says every round is expensive and to put all independent calls in one response, read several files at once, and merge quick shell commands; `fs_read` gained a `paths` list (up to 20 files, per-file errors) so file inspection stops costing a round per file; (2) **never wait** — the shell grace window and the `job_status`/`agent_result` caps already removed the 30 s p90 tool waits; (3) prompt caching is already ~93–100 % on both routes (verified in the Context inspector). What would NOT help: optimizing Lattice's request path (it is ~2 % of a round), and switching harnesses — a different client hitting the same gateway and model pays the same first-token latency; a faster *route* (e.g. a model with a lower first-token floor) is a bigger win than a faster client. The Run inspector now shows a **"Where the time went"** row per turn — rounds, summed first-token waits, model time, tool time — from per-round `usage` events that carry `round: true` with `ttftMs`/`wallMs` (and a final `toolMs`), so the round tax is visible in-app.
- **Density pass on the transcript** (2026-09-02). Tool rows no longer dump raw JSON: `toolResultView.ts` gives known tools a readable shape — a shell row shows its command and its output with an `exit N` chip, a job row one line per job (name, status, elapsed) with the output, an agent row one line per agent — and the prose the runtime addresses to the model (`note`, `hint`, `liveOutputNote`) is kept behind a "Note to the model" disclosure, with a Raw toggle for the original JSON. Incoming cards strip the instruction sentences meant for the model ("fold it into what you are doing…") while keeping the informative lead (status, exit code, purpose). The composer's background strip is one short line.
- **Live shell output is inline** (2026-09-02): a running command's output pane renders inside the tool row without expanding it — the same way an edit shows its diff — with the command beside the label; it folds into the Result once the command finishes.
- **The title follows the scope** (`shouldCheckTitleDrift` / `retitleOnDrift` / `parseDriftReply` in `runManager.ts`): after any completed turn that came from a substantial user message (≥40 chars), a thread named by the app or by the model gets a cheap drift check — the model sees the current name and the latest turns and answers KEEP or a new 3–6 word name — and is renamed only when the goal genuinely moved. Provenance is re-verified at write time and a human-typed name is never touched; `titleMsgs` advances either way so a turn is checked once. The system prompt and the `set_thread_title` description now say the model MUST rename on a significant scope shift (not for refinements/debugging of the same task).
- **Waits are capped, not advised** (2026-09-02, second pass). The prose did not hold: with the grace window in place the model parked itself through `job_status({wait:true, timeout_ms:590000})` instead. Now `job_status` peeks by default and a top-level run's wait is capped at 20 s (`JOB_WAIT_MAX_MS` / `jobWaitMs`), and `agent_result`'s first-finish wait is capped the same way (`AGENT_WAIT.maxMs`, race against the cap; an expired wait claims nothing, so the agents still deliver themselves) — both return the running statuses with a one-time "do not wait again; CONTINUE WORKING or end your turn" note. `bufferedByPipe` (`src/shared/commandHints.ts`) names a final `tail`/`head`/`sort`/`wc`… stage that swallows output until EOF: the job result and `job_status` say so (that was the empty "live output" on a ten-minute `… | tail -60`), the tool descriptions forbid the pattern, and the transcript's live-output pane explains the silence. Job rows in the transcript show the job's live elapsed time instead of the 1 ms the start call took.
- **Never block on slow work** (2026-09-02). A top-level run's foreground `shell` command is capped at a 20 s grace window (`FOREGROUND_GRACE_MS` / `foregroundGraceMs` in `builtin.ts`), whatever `timeout_ms` the model asked for: past it the command is promoted to a background job — still running, its output-so-far returned, its full output delivered as a new message on completion — and the tool result tells the model to CONTINUE WORKING or find a faster way, with the exact `job_status` peek call to check on it. (The trigger was a benchmark launched with `timeout_ms: 420000`: seven minutes of nothing.) A promoted job now exposes a **live peek** of the retired PTY's buffer (`ShellOutcome.peek` → `adoptShellJob({ peek })` → `BgJobView.output` while running), so `job_status wait:false` and the inspector show real progress instead of the promotion-time snapshot. The system prompt carries a matching doctrine paragraph ("NEVER BLOCK ON SLOW WORK … 99% of the time CONTINUE WORKING or FIND A FASTER WAY; waiting is the rare exception, and peek first"), and the tool notes/descriptions for `shell`, `start_job`, and `job_status` say the same. Subagents keep the classic hard timeout (nothing could ping them).
- **Cache diagnosis in the Context inspector** (`cacheInsight.ts`) and a **Tools inspector tab** (`toolInventory.ts` + `listTools` IPC, `toolStats.ts`) — see the roadmap entries for what each shows.
- **Sidebar activity strip** (`sidebarActivity.ts`): every thread with something going on — waiting on an approval/question, running, or failed while away — in one collapsible strip at the top of the sidebar with click-to-open and a per-thread Stop (`stopThreadWork` IPC → `cancelRunForThread`: the live run, every background subagent, every job).
- **Composer knows what "running" means** (`backgroundWork.ts`). The thread's running flag used to make the composer say "Steer the run…" and show Stop even when the reply was long finished and only subagents/jobs were working — the exact state that confused the parked-orchestrator session. `summarizeBackgroundWork` splits it: a streaming reply keeps steer/Stop; background-only shows a strip above the composer ("Working in the background: 2 subagents and 1 job … Open · Stop all"), Enter sends a normal message, and Stop all cancels every running agent and job on the thread (`stopBackgroundWork`).
- **Sidebar attention mark**: a thread with an approval or question parked on the user shows a pulsing amber dot (outranks the running spinner and the done/failed dots), so a stuck background chat is visible without a toast.
- **Drafts persist per thread** (`drafts` in the renderer store, mirrored to localStorage): switching chats or relaunching never loses what was typed; sending clears the draft.
- **Audible failures** (`src/main/notify.ts`). A main-run error, a subagent that died, a failed background job, an approval waiting, a question from the model, and (opt-in) a run finishing in the background now go out three ways, gated by Settings → General → Notifications (`notifications`: off / failures / attention (default) / all; `notificationSound`): a colour-coded in-app toast (`notice` push) that is clickable to jump to the thread and lingers longer for errors, a system notification when no Lattice window is focused (clicking it focuses the window and opens the thread), and the system alert sound when a window is focused. The policy is pure (`allowsNotice` / `planNotice`, unit-tested); the IPC push channel raises notices for run errors, approvals, questions, and finished runs, and the run manager raises them where a job or agent settles. The sidebar shows a red dot on a thread that failed while you were elsewhere (`failedThreads`), cleared when you open it or a new run starts. The error row also grew one-click fixes for the two output-shaped failures (an empty reply from a model that spent its budget thinking, or a reply cut off at the output limit): "Retry without thinking" (sets the thread's effort to off, then retries) and "Output limit…" (opens Settings).
- **Thinking (effort) path, audited end to end** (2026-09-02). Composer thinking control → `setEffort` → `updateThread` (persisted on the thread) → `startRun` reads `meta.effort` → `run.started` carries it → `streamChat` sends it: verified against the DB and the gateway's archived request bodies. Two real defects were hiding behind it. (1) "No thinking" never reached upstream: Lattice omitted `reasoning_effort` for off/none, and OmniRoute fills in the model's *default* effort when the field is absent, so thinking silently stayed on. Off is now sent explicitly as `reasoning_effort: "none"` (the gateway treats `none` as no-reasoning on every backend, including the Anthropic thinking mapping); only an absent preference (`undefined`, e.g. a non-reasoning model's title pass) omits the field. (2) The gemma4 route on Ollama 400'd on every turn (`cannot unmarshal array into Go struct field ChatRequest.messages.content of type string`) because prompt-cache breakpoints turn `content` into parts. `openChatStream` now flattens text-only parts back to strings (`flattenContentParts`) and retries once on that 400. Both 400 workarounds are memoised per model (`providerQuirks`) so a quirk costs one failed request per process, not one per round. The registry also accepts the gateway's `supportedReasoningEfforts` naming as the effort ladder.
- **Command purpose + live output**: `shell` and `start_job` take a `purpose` (3–8 words) that is the label the user sees — the tool row shows it as the title with the tool name dimmed beside it, the job card uses it as its name with the command beneath, the approval summary and completion ping quote it — and both tools tell the model to put the explanation there instead of comment lines inside the command. A running foreground command streams its PTY buffer to the transcript as `tool.progress` events (`ctx.progress` → `throttledProgress`, ≤1 snapshot per 350 ms, 6 KB tail) and the tool row's dropdown shows it live; a job (background or promoted) shows its live output from the jobs store by job id in the same dropdown.
- **Model picker recents**: the grouped layouts now lead with a real "Recent" / "Recent & used" section (the quick-pick set, filtered to the visible list) above the source/family groups, not just the chip strip.
- **Background jobs in the inspector**: the Agents tab lists the active thread's jobs (`listJobs`/`stopJob` IPC, `jobs.updated` push from `configureBgJobs`, plus a 1 s refetch while anything runs) as cards with the command, live elapsed time, status, a Stop button, and a 40-line live output tail; the tab badge counts running agents + jobs.
- **Retry**: an interrupted or errored reply that is still the thread's last message shows a Retry row in the transcript. `retryTurn` (run manager + `retryTurn` IPC) drops the failed reply and its run's events and re-runs the same user turn via `startRunFromHistory`, so no user bubble is duplicated; it refuses while the thread is busy or when later messages exist (other than the failed run's own steers).
- **Session messaging actually delivers**: `send_message` is R0 (it only reaches the user's own sessions/subagents), so it no longer parks on an approval card; and an idle recipient is **woken** with the message as a new turn (`delivery: 'woken'`, same push lane as a subagent completion) instead of getting an inbox row nobody reads until a human prompts that thread. Messages are marked read on delivery so `check_inbox` never re-delivers them.
- **Live drafting** for `shell`/`start_job` and `grep_search` was silently broken: the preview table keyed on `cmd`/`query` while the tools' arguments are `command`/`pattern`. Fixed (`DRAFT_FIELDS` in `runTimeline.ts`); a drafting shell row shows a terminal icon and the command as it streams, like a file write does.
- **Background jobs** (`src/main/tools/bgJobs.ts`): `start_job` — or `shell` with `background: true` — runs a command as a detached child process and returns a `jobId` at once; when the job finishes, its output is delivered back to the thread as a `⏳` user-role turn (attributed "Background command" in the transcript) that wakes an idle thread or is flushed when the busy run settles, so the model never has to poll. `job_status` reads or waits on jobs (bounded by `timeout_ms`, default 120 s), `stop_job` cancels them. A foreground `shell` command that outruns its timeout is promoted to a job the same way instead of being killed. Guard rails for weaker tool-callers: `shell` refuses a leading `sleep ≥15 s` while a job is running (and any sleep longer than the call timeout), and a foreground command that blocked ≥30 s returns a `hint` pointing at `start_job`. All three job tools are withheld from subagents, and a subagent's request for a background job is refused.
- `shell` runs against a **persistent PTY-backed login shell per thread** (`src/main/tools/ptyShell.ts`, using `node-pty`). Because it is an interactive login shell (`$SHELL -il`), it sources the user's profile, so the model gets the same PATH as Terminal — fixing the packaged-app failure where launchd's minimal PATH left `git`/`node`/Homebrew tools "not found". Working directory, exported variables, and shell state persist across calls. Each command is framed with a random sentinel (echo/prompt/bracketed-paste suppressed at init) to capture exactly one command's combined output, exit code, and resulting `$PWD`; timeouts and cancellation send Ctrl-C and keep the session reusable. Sessions idle-expire after 15 minutes and are killed on process exit. If `node-pty` can't load, it falls back to a one-shot `$SHELL -lc` (login) invocation so PATH is still correct, without cross-call state.

### Memory: shared store, Claude Code / Hermes bridge, and self-learning

Implemented in `src/main/memory/bridge.ts`, `src/main/runtime/selfLearn.ts`, and the memory paths of `src/main/runtime/runManager.ts`, `src/main/ipc.ts`, and `src/renderer/src/components/Inspector.tsx`:

- **One shared memory across three agents.** The bridge imports the user's Claude Code memory (global `~/.claude/CLAUDE.md`, this project's `CLAUDE.md`, and the per-project files under `~/.claude/projects/<slug>/memory`) and Hermes memory (`~/.hermes/memories/{USER,MEMORY}.md`) into Lattice's store, and exports Lattice-authored approved memories back into both. Imports carry a stable `mem:<store>:…` id so re-syncing updates in place and prunes items that vanished upstream; a missing or malformed store degrades to "found 0" rather than throwing. Lattice's own write-back is sentinel/prefix-tagged in each external store so it is never re-imported (no loop). Sync runs on launch, on every memory approve/edit/delete, at each turn boundary (import only, so a run never mutates an external store mid-stream), and on demand from the Memory tab's Sync button, which reports per-source found/added/updated/removed/exported counts.
- **On-demand recall, pinned-only injection.** `buildWireMessages` no longer dumps the memory store into every prompt. The `# Memory` section (built by `memoryPromptSection`, gated by `includeMemory`) is a byte-stable recall instruction telling the model to call `memory_search` before answering anything that could depend on stored context, plus only the *pinned* approved, unexpired, in-scope memories inlined in stable id order (capped at 40 items / ~6000 chars via `selectMemoriesForPrompt`). This keeps the first message small and — because the section contains no counts, no recency ordering, and no unpinned content — the system prefix stays byte-identical across turns, so memory activity no longer busts the prompt cache. Everything unpinned is reachable through `memory_search` exactly when relevant.
- **Model-proposed memory.** The `memory_save` tool lets the model propose a durable item (`proposed`, reviewed in the Memory tab); `memory_search` is a full-text read over approved items.
- **Self-learning.** After a run completes (gated by the `selfLearning` setting, on by default), a reflection pass reads the finished exchange and distills 0–N durable, reusable memories (preferences, stable facts, decisions, environment notes, warnings) as strict JSON. Parsing tolerates a stray code fence or a line of preamble; each item is validated (type/scope enums, confidence clamped to 0..1, content capped) and de-duplicated against existing memory (normalized containment) so the same fact is not re-learned every turn. High-confidence (≥ 0.75), non-sensitive learnings are stored `approved` when `selfLearningAutoApprove` is on — so they inject and export to Claude Code + Hermes immediately; low-confidence or credential-shaped items are always held as `proposed` for review. The whole pass is best-effort and runs after `run.completed`, so it never delays the turn or surfaces as a run failure. When anything is stored it pushes `memory.updated` and reconciles the bridge, closing the loop: Lattice learns → the shared store grows → Claude Code and Hermes see it too.

### MCP manager — partial

### Context and cache engine — partial

Context accounting now runs on a **real BPE tokenizer** (`src/main/runtime/tokenizer.ts`, backed by `gpt-tokenizer`), not the old chars/4 heuristic: `countTokens`/`estTokens` pick o200k_base for modern models and cl100k_base for legacy GPT-4/3.5, memoize by content, and hard-bound the worst case (oversized or degenerate repeated-char strings fall back to the ratio so budgeting can never hang). The budget, per-message `tokensOut` fallback, tool-schema sizing, and compaction sizing all count for real. **Stale tool-result pruning** also ships: `buildWireMessages` shrinks the result bodies (and images) of tool turns older than the recent keep-window to a byte-stable placeholder — reclaiming the largest, least-useful bulk in a long thread while keeping the recent working set and the assistant↔tool pairing intact — gated by the `pruneToolResults` setting and surfaced as `ContextBudget.prunedTokens` in the Context inspector. **Automatic threshold-triggered compaction** ships too: on send, once the context crosses `compactionThreshold`, `maybeAutoCompact` folds the history behind the just-sent turn into a summary (the current message is persisted first and preserved live), gated by the `autoCompact` setting; at `blockThreshold` the composer hard-stops a fresh turn with a banner and keeps the draft. Still planned: exact provider-usage replacement (`exact` stays false — tokenizer counts are estimates for non-OpenAI models), compaction checkpoint/rollback and locked turns, cache hit/miss diagnostics, and separate queue/model/tool timing.

The live budget tick (every ~400ms during a streaming reply) is now cheap by construction: `countTokens` memoizes every encoded string — long ones (large tool results, the exact strings that are expensive to re-encode, ~2ms per 60KB each) key by length+double-FNV hash so the memo never retains big content; `reclaimedByToolPruning` memoizes on the store's `toolWireRevision`, so a tick no longer re-reads and re-JSON-parses the whole thread (tool exchanges, attachments and all) from SQLite; and the settings/model-listing reads it makes are served from the in-memory store memos. Run-loop latency shaved elsewhere: the turn-boundary Claude Code/Hermes memory scan is throttled per workspace (20s TTL — it sat on the critical path between send and the first provider byte), `tool.drafting` events switch to a proportional-growth gate above a 4KB prefix so persisting a large streamed argument costs O(n) bytes instead of O(n²) (~10× less event-store/IPC traffic on a 24KB `fs_write`), and the persistent login shell is pre-spawned the moment the model starts *drafting* a `shell` call, so `$SHELL -il` profile sourcing (hundreds of ms) overlaps argument streaming and approval instead of preceding the first command.

**Cache breakpoints** use all four of Anthropic's marker slots: the system block, the two moving tail markers (last + second-to-last stampable message, tool results included, message-level on `role:'tool'`), and a **stable history anchor** — pinned at the end of the wire as the turn found it (`StreamRequest.cacheAnchorIndex`), byte-stable across every round of the turn, so the full conversation prefix is re-read even when a single round appends more blocks than the provider's ~20-block automatic lookback covers (a large parallel tool batch plus image carriers). Restamping stays idempotent and every message keeps the byte-stable parts form.

**Stall recovery** closes the "announced an action but never did it" failure — most visibly `openrouter/deepseek/deepseek-v4-flash-0731`, whose route leaks DSML tool-call control tokens into the text channel and drops the actual call, so a turn ends "Let me write the merged tooling directly." and finalizes complete with nothing done. Detection is two-tier: the SSE scrubber now *counts* the sentinels it strips and `streamChat` surfaces a `raw_tool_tokens` chunk (deterministic — the model provably tried to call a tool), and `endsWithActionIntent` catches routes that drop the call cleanly by matching a final sentence that commits to a concrete action verb ("let me write…", "I'll fix…" — never "let me know…"/"I'll wait…"). Either signal makes the run loop feed the reply back with a wire-only corrective nudge and continue, bounded at 2 per run (`MAX_STALL_CONTINUATIONS`), emitting a `retry` event that renders as a quiet inline notice in the transcript timeline. Both the main loop and subagent loops recover this way. A third tier, main loop only, closes the **parked orchestrator** failure (observed live on `openrouter/z-ai/glm-5.3-flash`, 2026-09-02): the model spawns background subagents with `run_agent(background: true)`, then ends its turn twenty seconds later on a promise — "While they run, I'll re-scan the corpus the moment the coder agent lands… I'll report back with receipts as each agent finishes." — without one further tool call, so the main model sits idle for the whole time the agents work. `endsWithDeferredPromise` matches a final sentence that is a first-person promise (any verb except a benign closer like "let me know…"/"I'll wait…"; a mid-sentence promise must also carry a deferral cue such as "once"/"the moment"/"as each"), and `classifyStall` only counts it while the thread actually has background subagents or shell jobs in flight (`runningBackgroundWorkLabels`). The nudge names the work in flight, restates that results are pushed back as new turns, and gives exactly two exits: do the independent work now with tool calls, or state in one line what you are waiting on. The `run_agent` background contract (tool description, tool result, and the `# Your tools` prompt note) was rewritten to match — it no longer offers "or end your turn" as a peer option to keeping working.

### Inter-session messaging — implemented

Implemented in `src/main/runtime/sessionMessaging.ts`, `src/main/tools/sessionTools.ts`, and `src/renderer/src/components/Inbox.tsx`. A "session" is a thread; one session can address and message another.

- **Directory + addressing**: `list_sessions` returns the other non-archived threads (id, title, model, running, unread), most-recent first. A target is resolved by exact id, then exact title, then a unique title prefix; ambiguous/unknown/self targets return a self-correcting error.
- **Two delivery lanes**: when the recipient has an active run, `send_message` steer-injects the message at its next safe boundary (folding it into work in progress, and persisting a user turn in the recipient transcript); when the recipient is idle, the message lands in its inbox only — no bubbles are written into a thread the user isn't watching. `check_inbox` drains the unread queue oldest-first and marks it read.
- **Reply routing** rides the ordinary tool: inbound text names the sender's id and `reply_to` links the original, so a reply is just another `send_message` back to that id.
- **Architecture**: the broker is a leaf module wired through callbacks (`configureSessionMessaging({ push, isRunning, steer })`) exactly like the ask/approval brokers, so it never imports the run manager and adds no import cycle. Persistence is a `session_messages` table (`db.ts`).
- **Policy**: the tools are `external_action` — `list_sessions`/`check_inbox` are R0 reads (available in every mode/preset), `send_message` is an R1 `submit` (allowed under Full, approval-gated under Auto, denied under Manual/Review and Plan). All three are auto-listed in the model's `describeTools` inventory with a capability note.
- **Renderer**: an `Inbox` panel (per-session inbox + directory + compose, reachable from a header button) shows an unread badge driven by a `session.message` push into `store.sessionUnread`; a message to a non-active thread also raises that thread's finished-run indicator. Covered by `sessionMessaging.test.ts` + `sessionTools.test.ts`.

### Files, browser, and artifacts — implemented

Three inspector tabs ship (`src/renderer/src/components/{FilesTab,TerminalTab,BrowserTab}.tsx`):

## Known issues carried forward

- The left rail can occasionally start collapsed in development even though the default state is expanded; root cause is unknown and low priority.
- Steering resumes only at the end of a provider response; provider-level mid-stream injection is not implemented.
- The active run snapshots the tool schema set at start. Policy is rechecked before each tool call, but changing permissions mid-run can leave a stale schema visible to the model until the next provider request.
- Tool schemas are now sent whenever the current mode/preset permits them, independent of provider-reported capability metadata (which gateways frequently omit or misreport — the previous cause of tool calls silently not working). - **One instance at a time** (`src/main/singleInstance.ts`). In dev the newest Electron instance takes the single-instance lock and the previous one yields, so an `electron-vite dev --watch` main rebuild replaces the running window instead of stacking a second one on stale code (electron-vite's own kill does not land on macOS). In production a second launch focuses the existing window.
